3x-ui can manage **multiple servers** from a single master panel, and override
how each inbound is advertised in subscriptions with **managed hosts**.

## Nodes

A **node** is another 3x-ui panel that your master panel manages over the node's
API. The master polls each node and shows its status, versions, CPU/memory,
uptime, and traffic in one place.

### Add a node

Provide the node's connection details:

| Field             | Notes                                                                 |
| ----------------- | --------------------------------------------------------------------- |
| **Name**          | Unique label (e.g. `de-fra-1`).                                        |
| **Scheme**        | `https` (default) or `http`.                                          |
| **Address / Port**| The node panel's host and port.                                       |
| **Base path**     | The node's web base path.                                             |
| **API token**     | A Bearer token created on the node (not needed in mTLS mode).         |
| **TLS verify**    | `verify` (default), `skip`, `pin` (pin a cert SHA-256), or `mtls`.    |
| **Inbound sync**  | `all` inbounds, or `selected` by tag.                                 |
| **Outbound tag**  | Optionally reach the node **through** a named outbound (egress bridge).|

The master verifies reachability when you add or test a node. It then sends a
**heartbeat** every few seconds, updating the node's status (`online` / `offline`)
and emitting `node.up` / `node.down` events (see the
[Telegram bot](/docs/operations/telegram-bot) and [Discord bot](/docs/operations/discord-bot)).

<Callout type="info">
  Nodes are identified by a stable per-panel GUID, so a node keeps its identity
  across restarts. A node can itself manage further nodes — the master surfaces
  those as read-only **transitive** sub-nodes (Node 1 → Node 2 → Node 3).
</Callout>

### Mutual TLS (mTLS) between master and node

For the strongest trust, use `tlsVerifyMode = mtls` (requires `https`):

<Steps>

<Step>
### Get the master's CA

On the master, fetch its node-auth CA certificate (the CA private key never
leaves the panel).
</Step>

<Step>
### Trust it on the node

Paste that CA into the node's "trusted CA" setting. It takes effect on the node's
next restart.
</Step>

<Step>
### Switch the node to mTLS

Set the node's TLS verify mode to `mtls`. The master now presents a client
certificate instead of an API token.
</Step>

</Steps>

## Agent nodes

An **agent node** runs a small program, `x-ui-agent`, that only runs Xray-core. It has no
panel, database or login of its own: the master keeps all inbounds and clients,
renders the node's whole Xray config and pushes it, and the agent applies it (hot when
it can, with a restart when it must) and reports status and traffic back. The node
keeps serving from its last good config while the master is down, and a config that
does not start is rolled back.

An agent node runs Xray-native inbounds only (VLESS, VMess, Trojan, Shadowsocks,
Hysteria, WireGuard). Protocols that need a sidecar on the node (MTProto, AmneziaWG,
TUIC, tproxy, NaiveProxy) stay on full-panel nodes.

<Steps>

<Step>
### Add the agent on the master

On the Nodes page choose **Add agent** and give a name, the server's address and a TCP
port (8443 by default). The panel creates the node and shows a **pairing bundle**
once. The bundle holds the agent's private key and secret and is never stored, so copy
it before you close the window.
</Step>

<Step>
### Install it on the server

Open the port in the server's firewall, then run this on the server as root:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/kuzzrus/3x-ui-awg/main/install-agent.sh)
```

Paste the bundle when asked (nothing is echoed). For an unattended install save it to a
file and add `--bundle-file <path>`. The installer needs systemd, checks the bundle
before it touches anything, downloads the release for the server's CPU and starts
`x-ui-agent.service`. Run it again without a bundle to update, or with `--uninstall` to
remove everything.
</Step>

<Step>
### Watch it come online

The node shows **online** after the first heartbeat and the master pushes its config
within seconds. Inbounds you attach to the node reach it on the next sync.
</Step>

</Steps>

**Pair again** (the key icon on the node row) creates a new secret and certificate when
the server was reinstalled or the bundle was lost. The agent that holds the old bundle is
cut off at once, so install the new bundle to bring the node back. An agent node's
secret, certificate pin and transport cannot be edited: they come with the bundle.

The row of an agent also has **Agent log**, the newest lines of its log with what Xray
printed, at the level you choose, and **Restart Xray**, which restarts the core into the
config the agent last ran. Connections through the node drop for a moment.

An agent is updated from the Nodes page like a panel node: the update button, or the
**Update available** tag, makes the agent run its installer again, on the latest release or
on the dev channel as the dialog says. It restarts onto the new version and keeps its
pairing bundle.

<Callout type="info">
  Traffic is counted on the master from the cumulative counters the agent reports, so a
  restart of the agent or of the master neither loses nor double counts usage, and a
  client that passes its quota is dropped from the agent's config by the next push, and
  comes back the same way when its plan renews.
</Callout>

<Callout type="info">
  The agent's core will not accept a config that reads a geo file it does not have. When a
  config needs one the agent lacks, the master sends its own copy before the config. Files
  the agent already holds are left alone: set **Geodata Auto-Update** on the dashboard and
  every agent's core keeps them current on that schedule.
</Callout>

### Route per node

The routing rules and outbounds of the master are one template, and every agent node runs
it. To run a rule on some agent nodes only, give those nodes the same **Tags** (for example
`ru`) in their settings, then pick the tag in the **Agent nodes** field of the rule on the
**Routing Rules** tab of the Xray settings. A rule with no node tags is for every core, the
panel's own and every agent's. A rule with node tags is for the agent nodes that carry one of
them, and not for the panel's own core. Tags are matched without regard to case, and a node
gets the new config on the next push.

Outbounds work the same way: the **Agent nodes** field of an outbound puts it on the agent
nodes that carry one of the tags only. The first outbound is the default of every core and
cannot be limited: to send the other traffic of some nodes through a node-only outbound, give
those nodes a rule that matches everything, with their tags. A rule or an outbound for every
core cannot send to or be chained through a node-only outbound, or a balancer of those only,
and an outbound that the panel's own features use (the panel outbound, the one a node is
reached through, an inbound's egress, the geodata download) cannot be limited to agent nodes:
the panel refuses to save either. If a rule for some
nodes sends to an outbound that a node with that rule does not have, the node still gets its
config, with the traffic of that rule blocked, and its status says which outbound is missing
and which tags give it.

### Tor and Psiphon on an agent node

Tick **Tor** or **Psiphon** under **Helper programs** in the settings of an agent node and the
agent runs that client beside Xray: a SOCKS proxy on `127.0.0.1:19050` (Tor) or
`127.0.0.1:19060` (Psiphon) of that server, started again with the agent even when the master is
out of reach. If the server lacks the program, the agent installs
it, which can take a few minutes: Tor with the package manager of the server, Psiphon by
downloading the binary the panel pins by its checksum, which exists for x86-64 servers only,
and it runs with the same bundled config as the panel's own Psiphon. The chip beside the
node's tags says **installing**, then **running** or **failed**, and pointing at it shows what the
program said last: how far Tor got in building a circuit, whether the tunnel of Psiphon is up, or
why it failed. An agent that is too old for helper programs says so as the last error of the
node: update it. Unticking a program stops it, and ticking it again tries at once after a
failure.

The outbound that the panel's own Tor uses, a `socks` outbound to `127.0.0.1` port `19050`
(`19060` for Psiphon), works as it is on an agent node that runs the program, and an agent node
that does not run it drops the traffic that a rule sends there. When only some nodes run it,
limit the outbound to them with its **Agent nodes** field; the panel's own core then no longer
has it.

### Decoy site on an agent node

Under **Decoy site** in the settings of an agent node, pick what anyone who probes the node is shown: a
page built into the panel, or a reverse proxy to a site you already host. It is the decoy of the panel's
own [reverse proxy](/docs/operations/reverse-proxy), on the node: a TLS listener on `127.0.0.1` and the
port you choose (7443 by default), which the REALITY fallback of the node reaches. Set the fallback target
of a REALITY inbound of this node to `127.0.0.1:<port>` yourself, and a probe that has no key is handed the
decoy; the Nodes page repeats the target in the info of the node.

The decoy needs a **domain** that points at the node and a certificate for it. **Automatic** gets one from
Let's Encrypt over HTTP-01, so port 80 of the node must be free and reachable; if the name does not point at
the node, or port 80 is shut, the chip beside the node says **certificate failed** and the tooltip says why.
**Files on the node** uses a certificate and a key that are on the server already, given by absolute path. A
probe that asks for another name than the domain gets no certificate at all. Each page looks a little
different on each node, so two nodes do not serve the same bytes.

<Callout type="info">
  The decoy of a node is its own. It has nothing to do with the reverse proxy of the panel, which serves
  the panel itself, and both can run at once on different hosts.
</Callout>

## Managed hosts

A **managed host** is an override endpoint attached to an inbound. At
subscription time, each enabled host renders an additional share link / proxy
with its own address, port, TLS, SNI, host header, path, and more — superseding
the older "external proxy" list. Use them to:

- front an inbound through a **CDN** (Cloudflare) with a different address/SNI,
- advertise **multiple domains** or per-region endpoints for one inbound,
- tweak ALPN, fingerprint, ECH, or mux per endpoint.

Each host has a remark (which supports the same
[template variables](/docs/config/share-links#remark-template-variables)), an
enable toggle, a sort order, and can be **excluded from specific subscription
formats** or **scoped to specific nodes**.

<Callout type="info">
  Hosts whose address/port point at a CDN let you keep the real server address
  private while clients connect through the CDN edge.
</Callout>
