3x-ui can manage **multiple servers** from a single master panel, and override
how each inbound is advertised in subscriptions with **managed hosts**.

## Nodes

A **node** is another 3x-ui panel that your master panel manages over the node's
API. The master polls each node and shows its status, versions, CPU/memory,
uptime, and traffic in one place.

### Add a node

Provide the node's connection details:

| Field             | Notes                                                                 |
| ----------------- | --------------------------------------------------------------------- |
| **Name**          | Unique label (e.g. `de-fra-1`).                                        |
| **Scheme**        | `https` (default) or `http`.                                          |
| **Address / Port**| The node panel's host and port.                                       |
| **Base path**     | The node's web base path.                                             |
| **API token**     | A Bearer token created on the node (not needed in mTLS mode).         |
| **TLS verify**    | `verify` (default), `skip`, `pin` (pin a cert SHA-256), or `mtls`.    |
| **Inbound sync**  | `all` inbounds, or `selected` by tag.                                 |
| **Outbound tag**  | Optionally reach the node **through** a named outbound (egress bridge).|

The master verifies reachability when you add or test a node. It then sends a
**heartbeat** every few seconds, updating the node's status (`online` / `offline`)
and emitting `node.up` / `node.down` events (see the
[Telegram bot](/docs/operations/telegram-bot) and [Discord bot](/docs/operations/discord-bot)).

<Callout type="info">
  Nodes are identified by a stable per-panel GUID, so a node keeps its identity
  across restarts. A node can itself manage further nodes — the master surfaces
  those as read-only **transitive** sub-nodes (Node 1 → Node 2 → Node 3).
</Callout>

### Mutual TLS (mTLS) between master and node

For the strongest trust, use `tlsVerifyMode = mtls` (requires `https`):

<Steps>

<Step>
### Get the master's CA

On the master, fetch its node-auth CA certificate (the CA private key never
leaves the panel).
</Step>

<Step>
### Trust it on the node

Paste that CA into the node's "trusted CA" setting. It takes effect on the node's
next restart.
</Step>

<Step>
### Switch the node to mTLS

Set the node's TLS verify mode to `mtls`. The master now presents a client
certificate instead of an API token.
</Step>

</Steps>

## Agent nodes

An **agent node** runs a small program, `x-ui-agent`, that only runs Xray-core. It has no
panel, database or login of its own: the master keeps all inbounds and clients,
renders the node's whole Xray config and pushes it, and the agent applies it (hot when
it can, with a restart when it must) and reports status and traffic back. The node
keeps serving from its last good config while the master is down, and a config that
does not start is rolled back.

An agent node runs Xray-native inbounds only (VLESS, VMess, Trojan, Shadowsocks,
Hysteria, WireGuard). Protocols that need a sidecar on the node (MTProto, AmneziaWG,
TUIC, tproxy, NaiveProxy) stay on full-panel nodes.

<Steps>

<Step>
### Add the agent on the master

On the Nodes page choose **Add agent** and give a name, the server's address and a TCP
port (8443 by default). The panel creates the node and shows a **pairing bundle**
once. The bundle holds the agent's private key and secret and is never stored, so copy
it before you close the window.
</Step>

<Step>
### Install it on the server

Open the port in the server's firewall, then run this on the server as root:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/kuzzrus/3x-ui-awg/main/install-agent.sh)
```

Paste the bundle when asked (nothing is echoed). For an unattended install save it to a
file and add `--bundle-file <path>`. The installer needs systemd, checks the bundle
before it touches anything, downloads the release for the server's CPU and starts
`x-ui-agent.service`. Run it again without a bundle to update, or with `--uninstall` to
remove everything.
</Step>

<Step>
### Watch it come online

The node shows **online** after the first heartbeat and the master pushes its config
within seconds. Inbounds you attach to the node reach it on the next sync.
</Step>

</Steps>

**Pair again** (the key icon on the node row) creates a new secret and certificate when
the server was reinstalled or the bundle was lost. The agent that holds the old bundle is
cut off at once, so install the new bundle to bring the node back. An agent node's
secret, certificate pin and transport cannot be edited: they come with the bundle.

<Callout type="info">
  Traffic is counted on the master from the cumulative counters the agent reports, so a
  restart of the agent or of the master neither loses nor double counts usage, and a
  client that passes its quota is dropped from the agent's config by the next push, and
  comes back the same way when its plan renews.
</Callout>

## Managed hosts

A **managed host** is an override endpoint attached to an inbound. At
subscription time, each enabled host renders an additional share link / proxy
with its own address, port, TLS, SNI, host header, path, and more — superseding
the older "external proxy" list. Use them to:

- front an inbound through a **CDN** (Cloudflare) with a different address/SNI,
- advertise **multiple domains** or per-region endpoints for one inbound,
- tweak ALPN, fingerprint, ECH, or mux per endpoint.

Each host has a remark (which supports the same
[template variables](/docs/config/share-links#remark-template-variables)), an
enable toggle, a sort order, and can be **excluded from specific subscription
formats** or **scoped to specific nodes**.

<Callout type="info">
  Hosts whose address/port point at a CDN let you keep the real server address
  private while clients connect through the CDN edge.
</Callout>
